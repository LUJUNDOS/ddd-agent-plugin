# verify —— 隔离验证（生产者/验证者分离）

## 触发
- 任何需要"验证通过 / 测试绿 / 可交付"的收口环节。

## 铁律（验收标准）
1. **隔离**：验证者不得与实现者同上下文。同上下文自验 → 判 FAIL。
2. **只对照 DoD**：验证者只核对契约的 `DoD` / 验收标准清单，不关心实现细节、不读实现源码猜行为。
3. **真跑真读**：验证者必须执行真实测试命令并读取真实输出（截图/日志/exit code），不得采信实现者的"已通过"自述。
4. **逐条打勾 + 证据**：每条 DoD 标 GREEN/RED，附「命令 + 输出片段 + 产出文件」。
5. **覆盖率门槛**：核心路径单测覆盖率 ≥ 80%（非核心 ≥ 60%）。用真实覆盖率工具报告判定，不估算。
6. **五类安全检查**：验证通过前过一遍安全清单（认证/鉴权/注入/数据暴露/配置风险），发现实际问题 → 标 RED 退回。
7. **结论落盘**：写验证报告（测试报告 + 闸门审计 + 覆盖率 + 安全检查 + 结论 GREEN/RED）。

## 安全检查清单（五类，固定检查项）
| 类别 | 检查点 |
|------|--------|
| 认证 | 登录/会话/Token 校验路径有测试覆盖；无硬编码凭证 |
| 鉴权 | 权限检查在服务端执行（前端隐藏≠安全）；越权路径有测试 |
| 注入 | 用户输入经参数化/转义；无字符串拼接 SQL/命令/HTML |
| 数据暴露 | 敏感字段不落日志/响应 |
| 配置风险 | 密钥走环境变量/密钥托管，不进代码库 |

- 五类清单的逐项判定细节见 `references/code-review-standard.md` §3；覆盖率门槛见 §4。

## 判 RED 的情形
- 验证者与实现者同一会话/同一上下文。
- DoD 任一条无真实输出佐证（仅靠声称）。
- 测试存在 no-fake-test 所列的假测试特征。
- 覆盖率不达标（真实工具报告数字）。
- 安全检查清单任一项发现实际问题。
- drift_check / ddd_gate 任一项不通过却声称绿。

## 纪律
- 绿 → 交 review 收口；红 → 退回执行代理修，重跑，不自行放宽标准。
