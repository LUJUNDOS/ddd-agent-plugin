# review —— 门禁覆盖（Done 之前）

## 触发
- 标记任务/契约 Done、合并分支、verify 给出 GREEN 之后。

## 双维度审查
| 维度 | 对象 | 依据 |
|------|------|------|
| 规格符合 | 代码是否符合文档/契约规格 | DoD 逐条 + docs 基准 |
| 代码质量 | 代码本身是否健康 | 质量检查清单（见下） |

## 验收标准（Done 的必要条件）
1. **真实测试绿**（经 no-fake-test 校验）。
2. **verifier GREEN**（独立上下文，见 verify 纪律）。
3. **reviewer PASS**：独立 reviewer 或用户 Oracle 对照 DoD 判过；自述"我做完了"无效。
4. **项目门禁覆盖**：若 DoD 提及 tdd / lint / 性能等，须有对应证据；缺一项即卡在审查关。
5. **质量审查无 Critical/High**：质量维度跑完清单，Critical/High 清零（Medium/Low 记录跟进，不阻塞）。
6. **完成标准自洽**：完成标准本身须列出上述门禁，否则干完仍卡审查。

## 代码质量检查清单（最低要求）
- [ ] **命名**：变量/函数/类名自解释，无拼音缩写/误导性命名
- [ ] **函数长度**：单函数 ≤ 50 行；参数 > 5 → 考虑参数对象；嵌套 > 3 层 → 提前返回/拆分
- [ ] **SOLID**：单一职责、开闭原则、依赖倒置（面向接口）
- [ ] **DRY**：同类逻辑重复 ≥ 3 处 → 提取；复制粘贴块必标记
- [ ] **Code Smells**：魔法数字、僵尸代码（未用 import/变量/分支）、全局可变状态、静默吞异常
- [ ] **错误处理**：异常路径明确处理或明确传播，资源有释放（finally/context manager）

## Severity 分级输出格式
```
## 审查报告
### 统计
Critical: N | High: N | Medium: N | Low: N
### Critical / High（必须修复）
- [级别] file:line — 问题描述
### Medium / Low（记录跟进）
- [级别] file:line — 问题描述
```
- **Critical**：安全漏洞、数据损坏、核心功能失效 → 阻塞
- **High**：明显逻辑错误、资源泄漏、性能瓶颈、违反已批准 AD → 阻塞
- **Medium**：可维护性、边界条件、规范偏差 → 记录跟进
- **Low**：风格、命名、可读性建议 → 可选

## 判未过审
- 任一项缺失 → 退回，不标 Done，不合并。
- 仅"代码写了"≠ Done；"测了"≠ 过了。
- Critical/High 未清零 → 不合并。

## 纪律
- reviewer 与 implementer 应不同人/不同上下文（复用 verify 隔离）。
- 升级：门禁冲突或 DoD 不可证 → 交用户裁定，不自行放宽。
