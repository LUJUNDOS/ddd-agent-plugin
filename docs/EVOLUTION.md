# EVOLUTION.md — 进化引擎系统规范

> **设计哲学**：进化是养成式而非侵入式。从每日工作日志中提取模式，固化为规则，在规则失效时主动退休。做到"同一类错误犯一次就够了"。

---

## 1. 数据源

不使用外部 feedback store 结构。进化数据直接来自已有的日志体系：

| 数据源 | 路径 | 内容 |
|--------|------|------|
| 每日日志 | `.workbuddy/memory/YYYY-MM-DD.md` | 每天的工作记录、教训、修复、发现 |
| 项目记忆 | `.workbuddy/memory/MEMORY.md` | 已沉淀的长期规则和约定 |
| 项目纪律 | `CLAUDE.md` / `CODEBUDDY.md` | 当前生效的 MUST 级规则 |

**优势**：无需额外采集步骤——日常写日志就是 L1 反馈采集，无需 feedback-observer sub-agent。

---

## 2. 进化层级 (Evolution Hierarchy)

### L1：日志沉淀（Log Accumulation）

**触发**：每次完成实质性工作后自动记录（已由系统规则强制执行）。

**动作**：在 `.workbuddy/memory/YYYY-MM-DD.md` 追加条目。关键信号词帮助扫描器定位：
- `修复` / `更正` / `Bug 发现` / `关键发现` / `教训`
- `根因` / `drift` / `硬编码原因` / `设计失误`

**标记**：L1_RAW（默认，无需显式字段——所有日志条目均为 L1）。

### L2：模式提取（Pattern Extraction）

**触发**：同一问题/教训在 N 天内出现 ≥ 2 次，或单次影响足够大（如 G0 软闸门漏洞导致 AI 绕过审批）→ 立即标记 L2 候选。

**动作**：`evolution_scan.py` 扫描日志，提取重复模式，生成规则提案。

**提案格式**：
```markdown
## 进化提案 E-{seq}

**触发日志**：2026-07-28 §3, 2026-07-30 §5
**模式**：{一句话描述重复出现的问题}
**根因**：{为什么反复出现}
**建议规则**：{拟新增到 CLAUDE.md / MEMORY.md 的规则文本}
**目标文件**：CLAUDE.md / CODEBUDDY.md / MEMORY.md
**风险等级**：低（规则新增）/ 中（规则修改）/ 高（架构调整）
```

**进化标记变更**：L1_RAW → L2_CANDIDATE

### L3：规则精化（Rule Refinement）

**触发**：L2 规则生效后又被同一模式触发 ≥ 2 次——说明规则不够精确，没有真正阻止问题。

**动作**：分析规则失效原因（措辞模糊？位置不对？触发条件不全？），生成规则修订提案。

**进化标记变更**：L2_CANDIDATE → L3_PENDING

### L4：结构进化（Structural Evolution）

**触发**：某类问题反复出现 ≥ 3 次，且当前规则体系无法覆盖——需要新增工具/脚本/契约类型来结构性地解决。

**动作**：生成结构性提案（新建 skill、新建契约模板、新建机械闸门）。

**进化标记变更**：L3_PENDING → L4_PROPOSAL

## 3. 规则退休（双向进化）

进化不仅是"加规则"，也是"减规则"。

### 退休候选条件

满足以下**任一**条件的规则，标记为退休候选：

1. **从未触发**：规则写入超过 30 天，在日志中从未被引用或触发（用 grep 验证）。
2. **已被内化**：AI 已稳定遵守，规则变成隐性知识，显式规则不再需要。
3. **被更上层覆盖**：新规则完全包含了旧规则的范围。
4. **前提条件已消失**：规则针对的工具/流程/模块已废弃。

### 退休流程

1. `evolution_scan.py` 在每次扫描时，将 30 天以上未被引用的规则标记为"退休候选"。
2. 与新增提案一起呈交用户审批。
3. 用户确认退休 → 从 CLAUDE.md/MEMORY.md 删除规则，在 EVOLUTION.md 变更历史记录"已退休"。

---

## 4. 进化标记生命周期

```
L1_RAW → L2_CANDIDATE → L3_PENDING → L4_PROPOSAL → [已采纳/已关闭]
                                                           ↓
                                                       (30天后检查)
                                                           ↓
                                                     [已退休 / 继续生效]
```

- **L1_RAW**：日志条目，未分析
- **L2_CANDIDATE**：模式重复 ≥ 2 次，候选规则新增
- **L3_PENDING**：规则新增后仍重复，候选修订
- **L4_PROPOSAL**：结构性解决方案，候选新工具/契约
- **已采纳**：用户确认，变更已执行
- **已关闭**：用户拒绝或不再适用
- **已退休**：规则超过 30 天未触发，已删除

---

## 5. 扫描触发时机

进化扫描是**里程碑驱动**的：

| 触发时机 | 说明 |
|----------|------|
| Phase 完成后 | 一轮 loop 结束（G3 验收通过）后手动运行 |
| 重大 bug 修复后 | 如果 bug 暴露了系统性漏洞 |
| 用户显式 "进化扫描" | 任何时候可手动触发 |

**不自动触发**的原因：项目初期规模小，自动每 session 扫描浪费资源且产噪。等项目进入 Phase 2+（有实际代码和测试数据）再评估是否加 session 级自动扫描。

---

## 6. 工作流

```
用户说"进化扫描" 或 Phase 完成
    ↓
python scripts/evolution_scan.py --since 2026-07-01
    ↓
扫描 .workbuddy/memory/*.md
    ├── L2 检测：同模式出现 ≥ 2 次 → 生成规则提案
    ├── L3 检测：已有规则被同一模式触发 → 生成修订提案
    ├── L4 检测：同模式 ≥ 3 次且无规则覆盖 → 生成结构性提案
    └── 退休检测：30 天以上未触发的规则 → 生成退休候选
    ↓
输出 proposals/evolution-scan-YYYY-MM-DD.md
    ↓
用户审批
    ├── 接受 → 执行（改 CLAUDE.md/MEMORY.md/CODEBUDDY.md）
    └── 拒绝 → 关闭提案，记录原因
    ↓
更新 EVOLUTION.md 变更历史
```
