# 法庭式对抗选型方法论

> 来源：SDD 全链路实战（抖音视频入库，kb/wiki/topics/sdd-full-chain-practice.md），经适配后融入 Synk DDD architect skill。
>
> 用途：architect skill Step 2（四维并行调研）+ Step 3（法庭式对抗选型）的详细规程。

## §0 核心理念

传统 ADR 是单视角分析——同一个角色写背景、列替代方案、下结论，盲区没人发现。法庭式对抗选型引入"红队"专门挑刺、"代言人"只说好话、"集成评估师"多维打分，最后由"法官"综合定案。核心价值：

1. **结构化盲区发现**：红队强制找缺陷，避免"列了替代方案但没深挖"
2. **复用举证**：从"选 A"变成"选 A 的 X 模块复用 repo-Y 的 Z 部分，工作量 2 人日"
3. **可追溯**：判决书 + 评分矩阵留档，未来复盘可追

## §1 四维并行调研（architect Step 2）

### 触发条件

architect 进入 Step 2 时无条件触发。从 01-requirements 的 FR-NNN 提取技术约束后，发起四个并行 Agent 子任务。

### 四维调研内容

| 维度 | 调研目标 | 产出 |
|------|---------|------|
| 竞品形态 | 同类产品/方案的产品形态、核心功能、技术栈 | `docs/research/competitors.md` |
| 数据来源 | 所需数据的合法来源、API 限制、成本、许可证 | `docs/research/data-sources.md` |
| 开源项目 | 可复用的开源项目/库，Stars、活跃度、许可证、维护状态 | `docs/research/opensource.md` |
| 实现方案 | 技术实现路径、已知坑、兼容性、性能基准 | `docs/research/implementation.md` |

### Agent 子任务 Prompt 模板

#### 维度 1：竞品形态调研

```
你是产品调研分析师。任务：针对以下技术约束，搜索同类产品/方案。

技术约束（来自 FR-NNN）：
{插入约束列表}

要求：
1. 搜索 3-5 个同类产品/方案
2. 每个记录：产品名、形态（App/Web/CLI/SaaS）、核心功能列表、公开的技术栈信息
3. 标注信息来源 URL
4. 不做评价，只做事实记录

输出格式：Markdown 表格 + 来源链接
```

#### 维度 2：数据来源调研

```
你是数据合规分析师。任务：确认以下数据需求的来源可行性。

数据需求（来自 FR-NNN）：
{插入数据需求列表}

要求：
1. 对每项数据需求，搜索可用的数据来源（API/开放数据集/爬取）
2. 记录：来源名称、获取方式、API 限制（QPS/配额）、成本、许可证
3. 标注是否有合规风险
4. 不做选型，只做可行性确认

输出格式：Markdown 表格 + 来源链接
```

#### 维度 3：开源项目调研

```
你是技术选型顾问。任务：搜索可复用的开源项目/库。

技术需求（来自 FR-NNN）：
{插入技术需求列表}

要求：
1. 对每项技术需求，搜索 2-3 个候选开源项目
2. 每个记录：项目名、GitHub URL、Stars、最后更新日期、许可证、主要语言、是否活跃维护
3. 记录已知 issue 数量和关键 issue
4. 不做选型，只做候选清单

输出格式：Markdown 表格 + GitHub 链接
```

#### 维度 4：实现方案调研

```
你是技术架构师。任务：调研技术实现路径和已知坑。

技术需求（来自 FR-NNN）：
{插入技术需求列表}

要求：
1. 对每项技术需求，搜索实现方案和最佳实践
2. 记录：实现路径、已知坑、兼容性问题、性能基准（如有）
3. 标注是否有平台限制（iOS/Android/Web/Windows/Linux）
4. 不做选型，只做路径梳理

输出格式：Markdown 分点列表 + 来源链接
```

### 调研产出规范

- 每份调研笔记 200-500 字，简短可读
- 写入 `docs/research/` 目录
- 所有事实必须附来源 URL
- 调研笔记是 Step 3 对抗选型和 Step 4 ADR 的证据底座

## §2 法庭式对抗选型（architect Step 3）

### 触发规则

| 候选方案数 | 模式 | 角色 |
|-----------|------|------|
| 0-1 | 跳过对抗 | 无（直接写 ADR，铁律 3 仍要求上网核实） |
| 2 | 轻量对抗 | 红队 + 法官 |
| 3+ | 全量对抗 | 代言人 + 红队 + 集成评估师 + 法官 |

### 全量对抗流程（3+ 候选）

#### 角色 1：代言人（Advocate）

每个候选分配一个代言人 Agent。代言人**只说优势**，这是设计意图——通过单边极化暴露每个候选的最强论点。

```
你是候选方案 {候选名} 的代言人。你的任务：只说 {候选名} 的优势。

候选方案：{候选名}
调研文档：{引用 docs/research/ 相关内容}
技术约束：{来自 FR-NNN}

要求：
1. 列出 3-5 条核心优势论点
2. 每条论点必须引用调研文档或搜索证据（附 URL）
3. 不提缺陷，不做对比——你的职责是让这个候选看起来尽可能好
4. 优势要具体，不要"社区活跃"这种空话，要"2026-07 月提交 312 次，活跃度排名前 5%"

输出格式：编号列表，每条 [论点] + [证据]
```

#### 角色 2：红队（Red Team）

红队对**所有候选**挑刺。红队的价值在于强制发现盲区——AI 自己写 ADR 时容易"列了替代方案但没深挖缺陷"。

```
你是红队分析师。你的任务：对所有候选方案挑致命缺陷。

候选方案列表：
{所有候选名 + 调研文档引用}

要求：
1. 对每个候选，挑 3-5 个致命缺陷
2. 每个缺陷必须基于事实（引用调研文档、GitHub issue、性能基准、搜索结果）
3. 缺陷要具体，不要"学习曲线陡"这种空话，要"异步错误处理需要手写 3 层 wrapper，issue #1234 2026-06 未修复"
4. 按严重程度排序：致命 > 严重 > 一般

输出格式：每个候选一个表格，列：[缺陷] [严重程度] [证据] [影响]
```

#### 角色 3：集成评估师（Integration Assessor）

```
你是集成评估师。你的任务：对所有候选按七维度打分。

候选方案列表：
{所有候选名 + 调研文档引用 + 代言人论点 + 红队缺陷}

评分维度（每项 1-5 分）：
| 维度 | 1 分 | 5 分 |
|------|------|------|
| 功能满足度 | 覆盖 <50% FR | 覆盖 100% FR 且有扩展 |
| 性能 | 明显瓶颈 | 超出预期 |
| 安全性 | 已知漏洞未修 | 通过安全审计 |
| 可维护性 | 文档缺失/社区萎缩 | 文档完善/社区活跃 |
| 社区活跃度 | <100 Stars/半年无更新 | >10k Stars/月提交 |
| 许可证 | GPL/AGPL（传染性） | MIT/Apache-2.0 |
| 复用成本 | 需大量改造 | 开箱即用 |

要求：
1. 输出评分矩阵（候选 × 维度）
2. 每个打分附一句话理由
3. 计算加权总分（功能满足度权重 ×2，其余 ×1）
4. 不做最终推荐——那是法官的事

输出格式：Markdown 表格 + 总分行
```

#### 角色 4：法官（Judge）

法官由 architect 自己担任——不是新 Agent，是 architect 综合所有输入做最终决策。

```
你是法官。综合以下输入，做出最终技术选型判决。

输入：
1. 四维调研文档
2. 代言人论点（每个候选的优势）
3. 红队缺陷（每个候选的致命问题）
4. 集成评估师评分矩阵

要求：
1. 写判决书：
   - 选谁、为什么
   - 关键缺陷如何缓解（具体措施，不是"后续优化"）
   - 被淘汰方案的核心原因（一句话每个）
2. 如果结果接近，说明决胜因素
3. 判决书不超过 300 字

输出格式：
## 判决书：{AD-NNN 标题}
**选定方案**：{候选名}
**核心理由**：...
**缺陷缓解**：...
**淘汰方案**：
- {候选 B}：...
- {候选 C}：...
```

### 轻量对抗流程（2 候选）

```
你是红队分析师。对以下两个候选各挑 3-5 个致命缺陷。

候选 A：{候选 A 名 + 调研引用}
候选 B：{候选 B 名 + 调研引用}

要求：同全量对抗红队规则。
```

法官直接做对比分析 + 定案（不需要代言人单边极化，两个候选直接对比即可）。

## §3 七维度评分表模板

```markdown
| 维度 | 权重 | 候选 A | 候选 B | 候选 C |
|------|------|--------|--------|--------|
| 功能满足度 | ×2 | __/5 | __/5 | __/5 |
| 性能 | ×1 | __/5 | __/5 | __/5 |
| 安全性 | ×1 | __/5 | __/5 | __/5 |
| 可维护性 | ×1 | __/5 | __/5 | __/5 |
| 社区活跃度 | ×1 | __/5 | __/5 | __/5 |
| 许可证 | ×1 | __/5 | __/5 | __/5 |
| 复用成本 | ×1 | __/5 | __/5 | __/5 |
| **加权总分** | | __/35 | __/35 | __/35 |

备注：
- 候选 A：{一句话理由}
- 候选 B：{一句话理由}
- 候选 C：{一句话理由}
```

## §4 复用举证表模板

复用举证把选型从"选 A"变成"选 A 的 X 模块复用 repo-Y 的 Z 部分，工作量 2 人日"——直接可执行。

```markdown
| 选定方案 | 复用来源 | 复用部分 | 改造量 | 工作量估算 | 风险 |
|---------|---------|---------|--------|-----------|------|
| {候选名} | {repo/库名} | {具体模块/文件} | {开箱即用/小幅改造/深度改造} | {人日} | {一句话} |
```

示例：

| 选定方案 | 复用来源 | 复用部分 | 改造量 | 工作量估算 | 风险 |
|---------|---------|---------|--------|-----------|------|
| Synk-Gateway | 自建 | Docker 容器 + Key 托管 | 全新开发 | 5 人日 | 无 |
| LLM 推理 | vLLM | 推理引擎 + API 兼容层 | 小幅改造（加脱敏中间件） | 2 人日 | 脱敏层性能损耗需测 |

## §5 与 DDD 闸门的关系

- 四维调研和对抗选型发生在 **G0 之后、G1 之前**（architect 阶段，产出 02-architecture.md）
- 调研文档（`docs/research/`）是 02-architecture.md 的附件，不独立走闸门
- ADR 中的对抗选型记录是 G1 闸门的审查材料——G1 检查 AD 完备性时，对抗选型判决书是"替代方案"部分的证据
- 如果 G1 审查发现对抗选型不充分（如红队缺陷基于错误事实），打回 architect 重做 Step 3

## §6 适用范围与限制

**适用**：
- 有 2+ 可行候选方案的技术决策（框架/库/基础设施/模型选型）
- 新项目首次架构设计
- 重大技术栈变更（迭代模式下的 AD 修订）

**不适用**：
- 只有一个可行方案时（跳过对抗，但仍需上网核实）
- 非技术选型决策（如产品功能取舍——那是 product-manager 的事）
- 纯视觉设计决策（那是 ui-designer 的事）

**限制**：
- Agent 子任务增加 token 消耗（全量对抗约多 3-5k token）
- 调研阶段增加 5-10 分钟（四个并行 Agent 搜索时间）
- 对于明显只有一个合理选型的决策，不要强行凑候选来跑对抗——浪费资源
