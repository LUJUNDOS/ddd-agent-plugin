# 代码审查标准（Code Review Standard）

> 状态：2026-08-13 建立。review / verify skill 的详细规程引用。范围：AI 全包模型项目（Synk 模型：executor 写码、verifier/reviewer 独立验证）。

## §0 双维度审查模型

审查 = **规格符合**（代码是否符合文档/契约）+ **代码质量**（代码本身是否健康）。

| 维度 | 执行者 | 依据 | 输出 |
|------|--------|------|------|
| 规格符合 | verifier（独立上下文） | DoD + docs 基准 | `validations/C-<slug>/run-<n>.md` |
| 代码质量 | reviewer（独立） | 本规程 §2 清单 | 审查报告（§5 格式） |

两者缺一不可：规格对但代码烂 → 质量维度卡；代码漂亮但规格不符 → 规格维度卡。

## §1 Severity 分级

| 级别 | 定义 | 处置 |
|------|------|------|
| **Critical** | 安全漏洞、数据损坏、核心功能失效 | 必须修复，阻塞合并 |
| **High** | 明显逻辑错误、资源泄漏、性能瓶颈、违反已批准 AD | 必须修复，阻塞合并 |
| **Medium** | 可维护性问题、边界条件未处理、规范偏差 | 记录跟进，不阻塞 |
| **Low** | 风格、命名、可读性建议 | 记录，可选 |

分级原则：宁可把疑似 Critical 标 High 交人裁定，不要把 Critical 降级为 Medium 自己放过。

## §2 代码质量检查清单

### 2.1 命名
- 变量/函数/类名自解释：读名字知道用途，不需要注释解释"为什么这样叫"
- 无拼音缩写（除非项目约定）、无语义不明的单字母（循环 `i` 除外）
- 布尔变量用 `is/has/can` 前缀；函数名动词开头

### 2.2 函数长度与参数
- 单函数 ≤ 50 行；超过即拆分信号（提取子函数/类方法）
- 参数 > 5 个 → 考虑参数对象
- 嵌套 > 3 层 if/for → 提前返回 / 卫语句 / 拆分

### 2.3 SOLID
- **S** 单一职责：一个类只有一个变化理由
- **O** 开闭：扩展新功能通过新增而非修改现有实现
- **L** 里氏替换：子类不破坏父类契约
- **I** 接口隔离：调用方不依赖它不用的方法
- **D** 依赖倒置：依赖抽象，不依赖具体实现

### 2.4 DRY
- 同类逻辑重复 ≥ 3 处 → 提取公共函数/组件
- 复制粘贴的代码块必标记（出处 + 差异点）

### 2.5 Code Smells（必须扫）
- **魔法数字**：裸数字出现在业务逻辑 → 命名常量
- **僵尸代码**：未使用的 import / 变量 / 分支 / 死代码路径
- **全局可变状态**：跨模块共享的可变单例
- **静默吞异常**：`except: pass` / `catch {}` 无日志无传播
- **超长行**：> 120 字符（按项目 lint 配置）

### 2.6 错误处理
- 异常路径有明确处理或明确向上传播
- 资源（文件/连接/锁）有 finally / context manager 释放
- 用户可见错误有明确信息，不泄露内部堆栈

## §3 安全检查清单（五类）

### 3.1 认证
- 登录/会话/Token 校验路径有测试覆盖
- 无硬编码凭证（密钥/密码/Token 出现在代码或提交历史）
- 会话过期/失效处理正确

### 3.2 鉴权
- 权限检查在服务端执行（前端隐藏 ≠ 安全）
- 越权路径（改 ID 访问他人资源）有测试
- 敏感操作（删除/改权限）二次确认或审计日志

### 3.3 注入
- 用户输入经参数化查询/转义，无字符串拼接 SQL/命令
- 前端渲染无 XSS 注入点（`dangerouslySetInnerHTML` / `v-html` 审查）
- 文件路径拼接防目录穿越

### 3.4 数据暴露
- 敏感字段不落日志/响应（手机号/身份证/Token 脱敏）
- 脱敏管线按 02-architecture 安全章节执行
- 调试输出（console.log / debug print）不带敏感数据

### 3.5 配置风险
- 密钥走环境变量/密钥托管，不进代码库（.env 已 gitignore）
- 默认配置（密码/端口/权限）已改或明确标注风险
- 第三方依赖无已知高危漏洞（能跑 `npm audit` / `pip-audit` 则跑）

## §4 覆盖率门槛

| 范围 | 门槛 | 判定方式 |
|------|------|---------|
| 核心路径（核心业务逻辑/跨模块边界/数据转换/脱敏） | **≥ 80%** | 真实覆盖率工具报告 |
| 非核心（工具函数/展示层） | ≥ 60% | 同上 |

- 工具：pytest --cov / c8 / istanbul 等，读报告数字，不估算、不声称
- **no-fake-test 真实性闸先行**：补测必须是真的（见 no-fake-test skill）
- 覆盖率不足 → 判 RED 退回补测

## §5 审查报告输出格式（固定模板）

```
## 审查报告
- 审查对象：<PR / branch / commit 或文件列表>
- 审查人：<reviewer 身份> | 日期：<date>
- 对照基准：<docs 版本 + DoD 列表>

### 统计
Critical: N | High: N | Medium: N | Low: N

### Critical / High（必须修复）
- [Critical] `file:line` — 问题描述
  - 依据：<违反哪条规范 / 风险后果>
  - Fix：<具体修改建议>

### Medium / Low（记录跟进）
- [Medium] `file:line` — 问题描述

### 结论
PASS / FAIL（Critical/High 清零 且 规格符合 → PASS）
```

## §6 与 DDD 闸门的关系

- 审查发生在 G3 验收阶段：**verify（真证 + 覆盖率 + 安全）→ review（规格 + 质量）→ 用户 Oracle**
- 质量审查发现 High 级 → 退回实现代理修，不允许带病合并
- 安全 Critical → 必须升级用户，不自行修复后沉默
- 本规程是纪律层（软约束）；ddd_gate.py 只做机械结构检查，不替代人工质量判断

## §7 适用范围与限制

- **适用**：AI 全包模型项目（Synk 模型）——executor 写码、verifier/reviewer 独立验证
- **不适用**：PATH-WISE 模型（AI 只测试/审查，生产码用户写）——用户代码质量由用户自己保证，AI 审查输出格式可参考但不可强加门槛
- **限制**：本清单是最低要求，不是完整代码规范；复杂项目按需扩展（并发、性能、可观测性等专项）
